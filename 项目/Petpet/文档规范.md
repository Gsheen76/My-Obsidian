# 文档规范

> [!summary] Summary
> Petpet 档案库的归类、命名与写入规则：**写作层**以 [[笔记/我的Markdown笔记规范与模板]] 为前提基础（frontmatter、摘要 callout、标题/列表/双链约定），本规范在其上叠加**项目层**的目录职责、命名规则与写入流程。仓库侧 `AGENTS.md` 的「Obsidian 实时记录」条款规定*何时必须写*，本规范规定*写到哪、叫什么、怎么写*。

## 1. 写作规范前提（基础层，先于本项目一切规则）

本库所有笔记**先遵守** [[笔记/我的Markdown笔记规范与模板]]，再叠加下文的 Petpet 专属规则。要点（细则以该文档为准）：

- **Frontmatter**：统一使用 `title / type / tags / summary / status / source / updated`（`migrated` 按需）；字段顺序照此排列；`tags` 用稳定主题词（本项目统一带 `project/petpet`）；`summary` 一句话说明这篇笔记有什么用。
- **正文骨架**：单 H1 标题；正文从 H2 开始；顶部紧跟 `> [!summary]` 一句话摘要；表格放参数/指标，代码块标注语言；命令、路径、函数、文件名用反引号。
- **收尾**：`关联笔记` 每条链接**必须带注释**（`[[笔记]]：为什么关联`）；`规划`/`资料来源` 无实际内容时省略，不留空壳章节。
- **事实纪律**：结论写可验证事实；日期等以 git 标签 / GitHub API / 文件实据为准，不确定标"待验证"。
- **双链**：新笔记至少连一个上级主题或索引；不为无实际关系的笔记强行互链。

## 2. 目录职责

| 目录 | 职责 | 收录内容 |
|---|---|---|
| `Petpet 总档案.md` | 项目级总览与维护总结 | 定位与当前状态、功能总览、架构、版本演进表、路线与风险、维护清单、档案馆目录索引 |
| `文档规范.md`（本文件） | 归档规则本身 | 写作前提、目录职责、命名规则、写入流程 |

## 3. 命名规则

### 3.1 开发记录（日志类，唯一需要日期前缀的目录）

格式：`YYYY-MM-DD 主题.md`

- 日期 = 该轮工作实际发生日；同日多轮可各自成文件，或并入当日同主题文件追加记录块。
- 主题写人话：改了什么，如 `2026-09-01 小屋按键两段式按压反馈`。
- 文件内部结构：背景 → 改动 → 验证 → 关联。

### 3.2 系统目录（场景/宠物/聊天/菜单/设置/工程结构）

格式：`主题 + 后缀.md`，后缀只允许以下四种：

| 后缀 | 用途 |
|---|---|
| `设计` | 方案、决策、拷问结论（为什么这么做） |
| `实施计划` | 分步执行计划（打算怎么做） |
| `实施记录` | 落地过程与验证结果（实际怎么做、结果如何） |
| `交互记录` | 交互演进与用户反馈轮次的沉淀 |

- 不加日期前缀；日期写在 frontmatter `updated:` 或正文标题里。
- 统一用「实施」，不写「实现」（历史文件已全部归一）。
- 主题与既有同族文件保持同词根（如 `商店信息与双列布局设计` ↔ `商店信息与双列布局实施计划`）。

### 3.3 发布系统

格式：`Petpet vX.Y.Z + 后缀.md`，后缀：`发布说明`（面向用户）、`发布设计`、`发布实施计划`、`发布实施记录`。固定入口：`版本规划与发布索引.md`。

### 3.4 总档案与其他根文件

根目录只允许：`Petpet 总档案.md`、`文档规范.md`、`源码启动.md`。新文件一律进目录，不再往根上放。

## 4. 归类判定（按顺序自上而下）

1. 与某个版本的发布/回滚/更新器有关 → `发布系统\`
2. 是方案/计划/实施沉淀，且属于某个功能领域 → 对应系统目录（场景/宠物/聊天/菜单/设置）
3. 代码结构、构建工具、参数调试器、仓库协作 → `工程结构\`
4. 其余（单轮 bug 修复、参数微调、视觉打磨、交互迭代、发版补录）→ `开发记录\` + 日期前缀

## 5. 总档案写入边界

**只写**：当前版本与状态行、功能总览、架构与资源总述、版本演进表、路线与风险、日常维护清单、档案馆目录索引。

**不写**：单轮开发日志（去开发记录）、发布细节（去发布系统）、具体设计决策（去系统目录）、逐轮用户反馈记录（去开发记录）。总档案的状态信息保持"最新一条"，历史靠版本演进表和各目录承载。

## 6. 写入流程（每轮开发动作的收尾步骤）

1. 按 §4 判定目录，按 §3 定文件名。
2. 按 §1 写作前提组织文件（frontmatter + 摘要 callout + 关联注释）。
3. 写入内容四要素：**改了什么 / 为什么改 / 如何验证 / 关联链接**。
4. 若本轮改变了项目状态（版本、当前开发方向、验证结果），同步刷新总档案 §1 的状态行。
5. 发版轮次另在 `发布系统\` 落发布说明/实施记录，并更新 `版本规划与发布索引`。
6. 仓库 `HANDOFF.md`/`AGENTS.md` 有变更时，同步副本到 `工程结构\`（同步件保持仓库原样，不加 frontmatter）。

## 7. 链接与维护义务

- 跨目录引用用带路径的 wikilink：`[[系统目录/文件名]]`、`[[开发记录/2026-09-01 某主题]]`；同目录内可用短名；指向库内其他区域（如 `笔记\`）用库根相对路径 `[[笔记/xxx]]`。
- **重命名或移动任何文件前，必须全库 grep 旧名并修复全部反向链接**；Obsidian 客户端内移动会自动改链，脚本/外部工具移动不会。
- 迁移、拆分、重命名等档案维护动作本身也记入 `开发记录\`（当日文件）。
