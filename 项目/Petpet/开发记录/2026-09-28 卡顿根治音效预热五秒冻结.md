# 2026-09-28 卡顿根治（音效预热五秒冻结）

> [!summary] Summary
> 「好卡顿」的量化定位与根治。应用级点击音过滤器、点击路径、idle CPU 逐一测排除且与 v1.7.5 基线对照无回归后，真凶落网：音效预热在 UI 线程同步执行冻 ~5 秒（每个 muted play 设备接入 ~200-460ms + stop ~240ms），启动后 2 秒触发正撞用户首次操作窗口。预热全部搬启动期一次付清，分栏切换从 5.3s 回到页面首建固有成本。

## 背景

全按键点击音轮重启后用户报「好卡顿，修复」。本轮三嫌疑：①应用级 eventFilter 每事件跨界（评审曾预警）②QSoundEffect stop+play 每点击音频后端工作（bounce sound 判例）③play_click 每次读盘 load_settings。

## 排查链（先量化后动手）

1. **live 进程 20% idle CPU**——但 offscreen 对照探针：过滤器 on/off 满速事件泵 95.7% vs 95.9%、自然流量 13.8% vs 13.4%——**过滤器无罪**。
2. **点击路径基准**：load_settings 单次 0.17ms、stop+play 0.002ms——**无罪**。
3. **v1.7.5 基线对照**（git worktree 同探针）：idle 12.5% vs 当前 13.4%——**无回归**；空闲开销（宠物 21fps 动画+每帧状态机/注册表 stat）是长期既有债。
4. **交互延迟基准**：商店开窗 1.4s、**切「套装」分栏 5.3s**（v1.7.5 同病：5.8s）——复现稳定。
5. **cProfile 定位**：5.3s 里 **5.06s 是 `_prewarm_sounds`**——7 个 QSoundEffect 的 muted play（466ms×7）+ stop（257ms×7）同步 for 循环压在 UI 线程；页面构建本身仅 56ms。触发点=启动后 2s `singleShot(2000)`——用户重启宠物后立刻测试，每次都撞进 5 秒冻结窗。
6. **分解实验**：`setSource`→Ready 的解码走后台不占主线程（免费）；**贵的是 play() 的设备接入**——进程首个 ~1s + 每实例 ~200ms，且同步/异步随音频设备唤醒状态漂移（裸跑 0ms、真机 885ms；疑似蓝牙音频省电唤醒）。

## 修复

- **预热全部搬启动期**：点击音在 `pet.py main()` 拿单实例锁后预热（把进程音频后端 init 掉）；宠物音效预热改 `PetWindow` 构造尾部同步执行（托盘/宠物未现，用户必无交互，一次付清 ~2.5s 最坏成本）。
- **`play_sound` 去 stop()**：play() 自带 restart 语义，stop 每次同步 ~240ms 纯多余；音量恢复（预热后保持 0）挪到播放时 `setVolume(0.5)`。

## 验证

- 显式 `_prewarm_sounds` 调用 0ms（设备活跃态全异步）；分栏切换首轮 500-990ms（每页首次构建）、二轮重访 60-104ms——首建成本经 profile 证实全在 Qt 原生段（Python 侧 <60ms），属固有权衡（记为已知项，用户再反馈则专项做预建页池）。
- 全量 **1016 passed**；重启 PID 18500，窗口正常、idle 13%（与基线持平）。

## 坑位沉淀

- **QSoundEffect 的 play() 同步段随音频设备唤醒状态漂移**（同机同码裸跑 0ms / 真机 885ms）——音频性能结论必须在设备活跃态复测，单次裸跑会误判「异步免费」。
- 「启动后延时预热」是伪异步：把同步成本从启动挪到用户操作窗口，等于把冻结瞄准了首次交互——**预热要么启动期同步付清、要么不做**。
- 性能投诉的排查顺序：先量化嫌疑（每个 ≤30 分钟的基准/对照），再 profile 真凶——本轮过滤器被评审预警为风险，实测无罪，避免了错误重构。
