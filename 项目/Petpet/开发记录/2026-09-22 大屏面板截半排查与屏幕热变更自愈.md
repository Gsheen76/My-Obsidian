# 2026-09-22 大屏面板截半排查与屏幕热变更自愈

> [!summary] Summary
> 「被截一半」不是落位代码的错：DPI 对齐活体复现 8 类窗口全部零溢出、实拍核验完整；真凶是**显示器配置在宠物进程存活期间变了**（双屏右屏 150% → 单屏 2560×1440@125%），旧进程按过期屏幕模型把窗口放在了已不存在/已变更的屏坐标上。修复方向选「自愈」：监听 Qt 屏幕信号，把所有可见顶层窗（含隐藏的宠物本体）钳回最近有效屏。

## 背景

- 用户 09-21 晚间反馈「你自己看看在大屏的效果现在，被截了一半」（此前一轮已做过面板全屏自适应 `center_window_on_screen`）。
- 取证时间线上有三个关键事实：
  1. 反馈时的复现记录是**双屏**（主屏 2560×1440 + 右屏原点 x=2560，右屏 150% 缩放——WinForms 视图 1707×960 证实）；
  2. 数小时后诊断时系统只剩**单屏** 2560×1440@125%（Qt logicalDpi=120）——显示器配置确实中途变过；
  3. 当时宠物进程无新崩溃（WER 最新 pythonw 是 09-20 已修的 SpeechBubble 案，crash_dump.log mtime 09-20 10:42）。

## 排查与取证

- **DPI 上下文对齐复现**（关键坑）：第一版复现脚本没调 `configure_display_scaling()` 就建 QApplication，与真实宠物进程（PerMonitorV2 + AA_DisableHighDpiScaling）上下文不一致，结论不可信。重写为**先调 configure_display_scaling 再建 app**，再逐项验证。
- 活体复现 8 类窗口（真 PetWindow + 真存档位置）：records / achievements / minigames / profile / settings（均居中 850×960）、shop、chat（自有收缩-居中数学上恒入界）、home 普通（1038×768）与装修全景（2138×768）——**当前代码 + 当前配置全部零溢出**。
- 实拍抓屏（`QScreen.grabWindow`）+ 视觉模型核验：records 面板四边完整内容正常、home 装修窗完整（「被设置窗遮挡」是测试脚本自己的叠窗，非缺陷）。
- 结论：反馈看到的截半来自**运行中进程的过期屏幕模型**；仓库 grep 证实**没有任何** screenAdded/screenRemoved/primaryScreenChanged 处理——桌面宠物应用常年经历拔插屏/改缩放，这是真实缺口。

## 改动

- `petpet/ui/common.py` 新增三个纯函数（与 `center_window_on_screen` 同族）：
  - `clamp_rect_into_screen(rect, screen_rect)`：只平移不缩放；窗口某轴比屏大时该轴对齐屏左上（不压缩）；
  - `pick_screen_rect_for(rect, screen_rects)`：最大重叠面积优先，全无重叠时中心距最近；
  - `clamp_window_into_nearest_screen(window, screen_rects)`：移动真窗口，返回是否移动。
- `petpet/app/pet_window.py`：
  - `__init__` 接线 `screenAdded/screenRemoved/primaryScreenChanged` → `_handle_screen_layout_change`；
  - 处理器：宠物本体**即使隐藏也钳**（防拔屏后重现悬空）；其余仅钳 `isVisible() and isWindow()` 的顶层窗（隐藏面板经 `show_near_pet` 打开时本来就按当下屏幕重落位）；
  - **救援半径 2000px**（桌面联合矩形外扩）：`_warm_up_interaction_surfaces` 把预热 BubbleMenu 停在 (-10000,-10000)（系统钳显 -8000），Qt.Tool 子件同样出现在 `topLevelWidgets()` 里——无半径会把它们拽进可见屏（真机枚举抓到的 4 个 -8000 窗口证实该风险真实存在）。

## 验证

- TDD：`tests/test_screen_layout_change.py` **16 测**（纯函数 5 + 选屏 3 + 包装 2 + 接线 4 含「预热面不动」「隐藏宠物也钳」）。
- **双轴 code-review（2026-09-22 追记）**：Standards 轴 0 硬伤（顺手清两处风格：顶层导入替代函数内导入、geometry() 只取一次）；Spec 轴抓到 2 项真问题并已修——
  1. **接线无测试钉住**（删掉 3 行 connect 依然全绿）→ 新增 disconnect 探针测试（对三个信号各尝试 `disconnect(handler)`，成功断开=证明 `__init__` 接过线，再接回）；
  2. **救援半径是绝对值**（桌面左缘 ≤-5528 的极端多左屏布局下停靠面落入救援区会被误拽）→ 处理器加 `_prewarming` 标记属性兜底，`_warm_up_interaction_surfaces` 同步给 `stat_bubble` 打标。
- 全量 **926 passed**（前值 910）；真平台冒烟（windows 平台，非 offscreen）：手动 emit `primaryScreenChanged` 真信号——悬空 850×960（x=3460）**精确**钳回 (1710,200)（frameless 无帧偏移）、(-10000,-10000) 预热面纹丝不动、基线 0 误伤。
- 重启源码宠物 PID 32620：可见于 (1882,919)，预热面照常停靠 -8000。

## 坑位

- **⚠ offscreen 平台手动 emit `primaryScreenChanged` 会把整个 pytest 进程 C 级硬死**（exit 127、无回溯、无 faulthandler 输出；真平台 emit 无恙属平台差异）——套件里验接线一律用 disconnect 探针，不 emit QGuiApplication 通知级信号。
- **管道 `pytest | tail` 的 `$?` 是 tail 的退出码不是 pytest 的**——判套件死活必须输出重定向到文件再看 EXIT（本轮曾因此误信两次「通过」）。
- **offscreen 窗管给可见窗 `move()` 叠加不定帧偏移**（同脚本单独跑 +2、全量环境 +9）——测试断言右/下缘留 16px 容差；生产面板 FramelessWindowHint 无此偏移。
- **pyqtBoundSignal 没有 `receivers()`**，且从类访问信号拿到裸 pyqtSignal 描述符（无 emit）——绑定信号只在实例上。
- 复现/诊断脚本必须**先 `configure_display_scaling()` 再建 QApplication**，否则 DPI 上下文与真实宠物不一致（本轮回炉重造的起因）。
- `QApplication.topLevelWidgets()` 包含带 Qt.Tool 窗口标志的**子件**——遍历「顶层窗」做全局操作时要把刻意停靠屏外的预热面排除（救援半径 + 标记属性双保险）。
