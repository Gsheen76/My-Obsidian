# Codex 介绍

## 1. Codex 是什么

Codex 是面向软件开发的 AI 助手。它可以在开发者授权的代码仓库和终端环境中理解项目上下文，协助完成代码编写、修改、调试、测试、文档整理和代码审查等工作。

它的重点不是只生成一段孤立的代码，而是围绕一个具体任务完成一组可验证的工程操作：阅读现有代码、判断影响范围、实施修改、运行检查，并说明最终结果。

## 2. 核心能力

### 代码理解

- 浏览目录结构、配置文件和源代码，快速建立项目上下文。
- 根据调用关系和现有约定定位问题，尽量复用项目已有的框架与工具。
- 解释函数、模块、错误信息和设计取舍。

### 代码修改

- 新增功能、修复缺陷、重构重复逻辑。
- 按现有代码风格编辑文件，保持改动范围清晰。
- 同步更新必要的测试、配置和说明文档。

### 验证与排错

- 运行单元测试、类型检查、构建命令或项目自带脚本。
- 根据测试失败信息追踪原因并迭代修复。
- 汇报已验证的内容、未能运行的检查以及剩余风险。

### 协作辅助

- 将较大的任务拆分为可执行步骤。
- 进行代码审查，优先指出会导致错误、回归或安全问题的风险。
- 帮助整理提交说明、变更摘要和后续工作项。

## 3. 典型工作流

```text
提出目标
  -> 检查仓库结构与相关文件
  -> 明确约束、影响范围和验收标准
  -> 实施最小必要改动
  -> 运行测试或其他验证
  -> 汇报修改内容与验证结果
```

一个好的任务描述通常包含以下信息：

- **目标**：希望实现什么结果。
- **范围**：允许修改哪些目录或文件。
- **约束**：需要保持的兼容性、风格、性能或安全要求。
- **验收标准**：怎样判断任务已经完成。

例如：

> 在 `src/auth` 中增加密码重置接口，沿用现有的错误响应格式；补充成功、过期和重复使用令牌的测试；完成后运行认证模块测试。

## 4. 如何写出有效提示词

### 直接说明结果

使用“实现、修复、补充、检查、解释”等明确动词，避免只描述背景而不说明期望产物。

### 提供必要上下文

指出相关文件、复现步骤、错误日志、目标平台和版本信息。上下文越具体，越容易得到符合仓库实际情况的修改。

### 分阶段处理复杂任务

对于涉及多个模块的工作，可以先要求分析影响范围和实施方案，再要求执行修改和测试。这样便于在中途检查方向是否正确。

### 要求验证

明确要求运行哪些测试或命令，并让 Codex 汇报验证结果。没有验证的代码修改不应默认视为完成。

## 5. 权限与安全

Codex 的操作范围由当前环境授予的权限决定。涉及写文件、执行命令、网络访问或其他外部影响时，应遵循最小权限原则，并关注以下事项：

- 不要把 API 密钥、密码、令牌等敏感信息写入代码或提交记录。
- 对删除、覆盖、批量移动文件等不可逆操作先确认目标和范围。
- 对外部服务调用、依赖安装和发布操作检查命令及目标环境。
- 不要因为测试暂时失败就跳过测试或掩盖错误。
- 保留与任务无关的用户改动，不随意重置或覆盖工作区。

## 6. Codex 适合做什么

- 修复有明确复现步骤的缺陷。
- 为现有模块补充测试和文档。
- 实现边界清晰的小型功能。
- 阅读陌生代码并梳理架构。
- 进行有测试保护的重构。
- 协助处理重复、机械但需要保持一致性的工程工作。

对于需求目标、数据来源或安全影响都不明确的工作，应先补充信息或缩小范围，再开始修改。

## 7. 一个实用的任务模板

```text
目标：

背景或问题：

相关文件/目录：

约束：

验收标准：

需要运行的验证命令：
```

## 8. 相关概念

- **上下文**：Codex 用于理解任务的代码、配置、日志和对话信息。
- **工作区**：当前允许读取和修改的项目目录。
- **工具调用**：读取文件、执行命令、应用补丁和运行测试等具体操作。
- **验证**：用测试、构建、静态检查或人工检查确认修改符合预期。
